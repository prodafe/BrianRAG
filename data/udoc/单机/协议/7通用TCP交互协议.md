## 一、概述

本协议描述在机器人对接过程中与调度的交互过程和协议，原有的机器人同类别的交互mode有ModeSocket,ModeSocket2,Inform,Confirm等等。
为了减少后续的重复开发，故确定一种通用的流程和协议。

## 二、消息格式

TCP客户端和服务端交互的数据包格式都遵循以下格式
```
$#LEN##DATA$~
```

 - $#: 数据包开头
 - ##: 分隔符，用于分割长度和数据
 - $~: 数据包结尾
 - LEN: DATA数据长度的ascii码值
 - DATA: json对象字符串,必须包含`#ID#`、`#CMD#`和`job_id`

示例:
```
$#9##{"K":"V"}$~
```

其中LEN部分为字符串`"9"`，因为数据DATA部分{"K":"V"}的长度为9。

## 三、交互内容

交互过程中调度系统作为TCP服务端，机器人作为TCP客户端，由机器人端先发起连接和请求，
机器人发送的数据内容如下所示(由于格式已由上一章节描述清楚，后续的数据包不再强调格式，只描述DATA部分的数据):

```json
{
	"#ID#": "机器人唯一id(名称)",
	"#CMD#":"指令", 
	"mision_id": "xxxxxx",
	"req_id": "1",
	"parameters":{} // 其他参数
}
```

机器人发送的数据包必须包含以下key:
 - `#ID#`: id为机器人的唯一ID，是为了兼容短连接的方式，服务端需要根据ID判断当前新连接和之前的某次连接是否属于同一个请求过程，前后使用`#`包围是为了防止json对象中key重复
 - `#CMD#`: 此次请求的命令字，用于区分此次请求的主要指令
 - `mission_id`: 此次请求是为了完成哪一个之前调度系统下发的任务，防止任务切换了，调度系统内部保留的信息为上个任务的，避免返回错误的数据
 - `request_id`: 当前请求的唯一序列号，主要发给调度系统，让调度系统区分是否是同一个请求，如果是同一个请求，调度系统会继续处理，如果是不同请求，则之前的请求会被强制结束掉，然后开始处理新的请求

**注意：`#ID#`用于让调度确定是某一台机器人，同一个机器人同一时间只能有一个请求任务在执行，`#CMD#`是用来区分请求的指令，`mission_id`+`request_id`是用来区分请求是否重复的，如果同一个route中包含多个请求过程，则必须用`request_id`来区分，防止调度端以为当前的请求和之前的请求是重复的，导致直接返回`finished`，如果一个route中只有一个请求过程，或者多个请求的过程`#CMD#`指令都不一样，则可以省略`request_id`。**

服务端返回数据的格式如下：
```json
{
	"#ID#": "机器人唯一id(名称)",
	"#CMD#":"指令",
	"mission_id": "xxxx",
	"request_id": "1",
	"state": "created/started/executing/succeed/failed/finished",
	"action":
	{
		"sound":"已收到/对接中",
		"light":"green/yellow"
	},
	"code": 200,
	"message": ""
}

```

服务端返回的数据包必须包含以下的key:
 - `#ID#`: 与机器人发送的值一致，机器人端可以通过该字段验证是否应该处理
 - `#CMD#`: 与机器人发送的值一致，机器人端可以验证当前是否应当处理该数据
 - `mission_id`: 与机器人发送的值一致，机器人端可以验证是否是当前任务的返回数据
 - `request_id`: 与机器人发送的值一致，机器人端可以验证是否是当前请求返回的数据
 - `state`: 服务端对于机器人请求的处理状态，分为以下几个步骤，如果不需要细分这么多，可以适当跳过一些流程:
	 - created: 服务端已经接收到机器人端的请求
	 - started: 服务端已经开始处理机器人的请求
	 - executing: 服务端对于机器人的请求正在处理中
	 - succeed/failed: 服务端对于机器人的请求处理成功或者失败
	 - finished: 服务端已经发送过succeed/failed状态的返回数据，此次请求过程已经结束，后续不会再有请求处理的状态的变化

可选的key如下:
 - `action`: 服务端可以通过该字段控制机器人的一些提示行为，如报警灯颜色的控制、语音播放，内部`sound`字段表示让机器人播放的语音音频文件名称，`light`字段表示控制机器人报警灯颜色。
 - `code` & `message`: 返回的状态码和消息，如服务端处理请求过程中一些报错信息、原因等。


## 四、交互流程

交互的流程分为同步长连接方式和异步短连接方式。
1. 同步长连接方式的过程如下图所示：

![tongyongTCP交互协议-同步方式](通用TCP交互协议-同步方式.png)

同步长连接的方式在交互过程中保持TCP的长连接，一直到调度完成请求的处理，步骤如下：
1) 首先由本体发起TCP连接，调度端有同时连接的数量限制，如果失败应当尝试重新连接
2) 连接成功后，本体发送请求，调度端应当立即返回`created`状态的数据包
3) 收到`created`数据包后不用断开连接，后续由调度端不断反馈当前处理的过程数据包，该过程中本体应当对数据包中`action`字段的提示作出适当的输出反馈，使外界收到一些处理的过程信息
4) 当收到`succeed/failed`数据包后，本体可以断开连接，也可以等待收到`finished`之后断开连接，这三个状态都表示处理结束了，本体可以根据`failed`状态发起重试请求的过程。

**注意：如果调度端处理返回`failed`->`finished`，本体再次发起重复的请求，调度端会重新开始处理，但是如果调度端返回`succeed`->`finished`，本体再次发起重复请求，调度端会认为之前的消息本体没有收到，直接返回`finished`，不会再次重新处理请求**

2. 异步短连接的过程如下图所示：

![通用TCP交互协议-异步方式](通用TCP交互协议-异步方式.png)

异步短连接的方式在交互中进行多次TCP短连接，中间可能会漏掉一些调度端的返回数据的过程，但是可以释放本体，不必等待调度端，可以发送请求之后先做其他任务，再查询调度执行的结果：
1) 首先，与同步长连接方式相同，本体先发起TCP连接，连接成功后发送请求，调度端必须回复数据包表示已经收到请求，返回的数据包状态一般是`created`，本体收到调度返回的数据包之后就可以断开了
2) 后续由本体再次重新发起TCP连接，发送同样的请求数据包，调度端会立即返回当前的执行状态和结果，可能会有`action`数据
3) 如果网络正常的情况下，本体后续查询过程中必然会收到一次`suceed`或`failed`状态的返回包，调度端只有发送过一次`succeed`或`failed`数据包之后，调度端的处理状态才会变成`finished`，后续本体再次发送同样的请求只会收到`finished`状态返回包，与同步长连接相同的是：如果处理结果是`failed`，本体再次发送同样的请求，调度端会重新处理该请求指令，如果处理结果是`succeed`，后续再次发起同样的请求，调度端只会返回`finished`状态包，不会重新处理。

以上两种方式本体和调度端都应当支持，推荐使用异步短连接方式，对于网络的依赖较小。
