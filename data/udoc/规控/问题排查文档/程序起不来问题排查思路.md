## 一、概述
该文件描述了jarvis-g在启动后程序起不来的情况下的排查思路，列举了几个可能导致起不来的问题。

## 二、log目录下生成了新的log
这里主要是针对jarvis-g起不来的情况，其他软件导致的起不来，即jarvis-g日志还在正常打印的情况下，一律按照没有生成新log的步骤排查。

判断程序是否是正常结束，判断条件是查看最新的log最后内容是否如图
![程序正常结束.png](/规控/image/程序正常结束.png)  
log最后内容和图片一样说明是程序正常结束

### 程序是正常结束   
在log文件夹中的log日志中搜索下列打印
#### waiting for laser ready
当搜索到这个打印时通常说明机器人主激光没有数据 
1. ping 10.8.8.10,如果ping不通，检查激光是否通电或者主激光网线是否连好
2. 检查主激光指示灯是否异常
3. 如果能ping通ip且主激光指示灯无异常，需要联系相关人员进行检查激光驱动配置

#### waiting for robot ready   
当搜索到这个打印时通常说明机器人上位机和下位机没能通讯上
1. 关机重启，观察是否能够复现
2. rostopic echo /jodom 使用该命令查看是否有有数据，如果没有数据联系相关下位机人员排查。（通常原因是jarvis_base.launch文件配置错误）
		jarvis_base.launch的配置问题通常有两个：
    1. 串口的APP使用了网口的配置，或网口的APP使用了串口的配置
    2. 串口配置的端口异常
    3. 网口配置的app没有配置192.168.2.10的ip
3. 如果有数据，执行以下步骤来增加启动延时，进行尝试
4. roscd 工程名/launch（不确定工程名使用cat /etc/ros/noetic/urobot.d/bringup.launch |grep find 查看）
5. 打开jarvis_g.launch，增加prefix="bash -c 'sleep 后面的值，并重启服务。多次增加没有效果请联系相关人员排查

#### receive nothing for a long time
当搜索到这个打印，通常是由于上下位机在刚开机时的通讯不是很稳定，导致上下位机断连，从而导致程序挂。
处理方法基本与waiting for robot ready 一致，区别是这种情况下，jodom通常都是有数据的。增加启动延时即可。

#### 没有这两个打印
可能原因：
1. 如果是老的程序换成新的程序起不来了，检查service/fault.json这个文件是否有错误码的相关内容，如下图所示。
![error_code.png](/规控/image/error_code.png)
2. 待补充
### 程序是突然崩溃
该情况通常为routes或某些配置文件存在异常导致程序崩溃，点击[此链接](https://p10j68f02n.feishu.cn/docx/YLMTdfXIkorB8Dx4nYSccvIKn8b?from=from_copylink)下载check_data检查json格式  
确认json格式无异常请联系相关人员排查
## 三、log目录下没有新的log
1. 某些文件缺少权限，使用以下指令赋予权限。执行结束后重启
```
sudo chmod 777 -R /usr/local/urobot
sudo chown -R ucore:ucore /usr/local/urobot
```
2. 地图文件存在异常。重新上传地图并重启
3. 单起程序进行排查。具体步骤如下：
   ```
   1. 使用top指令，检查除了jarvis-g的程序是否正常允许，主要检查有无nodelet和bz_robot
   2. 关闭服务，sudo systemctl stop urobot
   3. 如果正常有nodelet和bz_robot，那么roslaunch 工程名 jarvis_g.launch，报错后截图发给相关人员
   4. 如果没有nodelet和bz_robot，那么roslaunch 工程名 bringup.launch，报错后截图发给相关人员
   5. 不确定工程名使用cat /etc/ros/noetic/urobot.d/bringup.launch |grep find 查看
   ```
4. 如果执行第三步时发现等了一段时间程序正常起来了，那么可能是机器人配置的工程名不正确。
4. 某些启动文件存在问题。检查修改的文件（联系对应对应人员排查）或者拷贝正常的机器人中的urobot整个文件夹替换（替换前务必做好原来的urobot文件的备份）。
5. 还是存在异常需要联系相关人员排查
